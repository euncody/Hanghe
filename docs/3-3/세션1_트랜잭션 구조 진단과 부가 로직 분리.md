이 세션의 설명을 쉽게 풀면, **트랜잭션을 단순하고 가볍게 유지하자**는 메시지입니다. 주요 내용을 단계별로 설명해볼게요.

---

### **1. 트랜잭션은 핵심 로직만 담아야 한다**

트랜잭션(Transaction)은 데이터베이스에서 작업을 “한 덩어리로 묶어 처리하는 단위”예요.
예를 들어, 도서 예약 기능을 생각해보면:

* 예약 테이블에 신규 예약 데이터 입력
* 재고 수량 감소
* 사용자 로그 기록

이 세 단계가 하나로 묶여야 예약이 “정상적으로 완료”되죠. 이게 트랜잭션의 **핵심 로직**입니다.

하지만 이 안에 “알림 문자 발송”, “외부 API 호출”, “로그 분석 데이터 전송” 같은 **부가 로직**을 넣으면 문제가 생깁니다. 트랜잭션이 길어지고 복잡해지면서 장애 가능성이 커지거든요.

---

### **2. 부가 로직이 트랜잭션을 오염시키는 문제**

부가 로직이 트랜잭션 안에 들어가면 이런 일이 생깁니다:

* **지연**: 외부 API 응답이 늦어져 트랜잭션이 오래 유지됨 → DB 락 증가로 다른 요청도 대기
* **실패 전파**: 외부 시스템이 잠시 죽었을 때 → 전체 트랜잭션이 롤백됨
* **성능 저하**: 많은 요청이 몰릴 때 장애로 이어짐

즉, 중요한 DB 작업과 덜 중요한 부가 작업을 같은 트랜잭션에서 처리하면 서비스 전체가 위험해질 수 있습니다.

---

### **3. 핵심 vs 비핵심 로직 구분 기준**

* **핵심 로직**: 데이터 일관성을 보장해야 하는 필수 작업

    * 예: 예약/결제 데이터 저장, 재고 차감
* **비핵심 로직**: 서비스 경험은 좋게 하지만, 실패해도 치명적이지 않은 작업

    * 예: 알림 발송, 로그 전송, 분석용 이벤트 기록

---

### **4. 비동기 처리로 부가 로직 분리**

부가 로직은 \*\*트랜잭션 밖에서 비동기(Async)\*\*로 처리하는 게 이상적입니다.

예시:

* 예약 DB 저장 트랜잭션은 성공하면 즉시 커밋
* 커밋이 끝난 후 \*\*이벤트 큐(Kafka, RabbitMQ, Redis Pub/Sub 등)\*\*나 **비동기 Task**로 알림 발송 작업을 따로 실행
* 알림 실패 시에도 예약 데이터는 정상적으로 유지됨

---

### **정리**

| 구분     | 트랜잭션 안          | 트랜잭션 밖(Async)        |
| ------ | --------------- | -------------------- |
| **목적** | 데이터의 완전성 유지     | 사용자 경험/부가 기능 제공      |
| **예시** | 예약 정보 저장, 재고 감소 | 문자 알림, 로그 전송, 분석 이벤트 |
| **장점** | 안정적 데이터 처리      | 장애 전파 차단, 시스템 성능 개선  |

---

이 세션의 핵심 메시지는:

> **“트랜잭션을 짧고 가볍게 유지하라. 부가 로직은 분리해 비동기로 처리해라.”**
> 이렇게 하면 시스템 안정성과 성능을 모두 잡을 수 있습니다.

---
