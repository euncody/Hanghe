예시는 “**주문이 완료됐을 때 여러 가지 후속 작업을 처리하는 구조**”를 보여주고 있습니다.

---

## **1. 이벤트 클래스**

```kotlin
data class OrderPlacedEvent(
    val orderId: Long,
    val userId: Long
)
```

* **이벤트의 데이터 틀**이에요.
* `OrderPlacedEvent`는 **주문이 발생했음을 알리는 메시지** 역할을 합니다.
* `orderId`, `userId`는 “이 주문은 누구의 어떤 주문인지”를 식별하는 정보죠.

---

## **2. 이벤트 발행 (Publisher)**

```kotlin
@Service
class OrderService(
    private val eventPublisher: ApplicationEventPublisher
) {
    fun placeOrder(orderId: Long, userId: Long) {
        // 1. 핵심 로직: 주문을 DB에 저장 (여기는 간단히 생략)
        // 2. 이벤트 발행
        eventPublisher.publishEvent(OrderPlacedEvent(orderId, userId))
    }
}
```

* 주문을 저장하는 **핵심 로직**을 실행한 후,
  `eventPublisher.publishEvent()`로 `OrderPlacedEvent`를 발행합니다.
* 이때 `OrderService`는 “이벤트를 발행했다”는 사실만 알고,
  이 이벤트로 무엇을 할지는 전혀 모릅니다.

---

## **3. 이벤트 구독 (Listeners)**

이제 이벤트를 받아서 **각 관심사별로 분리된 작업**을 실행합니다.
여러 개의 리스너가 같은 이벤트를 독립적으로 처리할 수 있습니다.

---

### **(1) 재고 차감**

```kotlin
@Component
class InventoryListener {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    fun handle(event: OrderPlacedEvent) {
        println("재고 차감 처리: ${event.orderId}")
    }
}
```

* 주문이 성공적으로 DB에 커밋된 후 재고 차감을 실행합니다.
* `AFTER_COMMIT` 덕분에, **주문이 롤백되면 이 로직은 실행되지 않습니다.**

---

### **(2) 알림 발송**

```kotlin
@Component
class NotificationListener {
    @Async
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    fun handle(event: OrderPlacedEvent) {
        println("알림톡 발송: ${event.userId}")
    }
}
```

* 알림톡을 보내는 작업입니다.
* `@Async`를 붙여서 **비동기**로 처리하므로, 알림 발송이 늦어도 메인 로직은 빠르게 종료됩니다.

---

### **(3) 통계 적재**

```kotlin
@Component
class AnalyticsListener {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    fun handle(event: OrderPlacedEvent) {
        println("주문 통계 적재: ${event.orderId}")
    }
}
```

* 주문 데이터를 통계 시스템에 적재합니다.
* 이 작업이 실패하더라도 재고 차감이나 알림 발송에는 영향을 주지 않습니다.

---

## **4. 동작 흐름 요약**

| 단계          | 설명                             | 실행 주체 |
| ----------- | ------------------------------ | ----- |
| 1. 주문 발생    | `OrderService.placeOrder()` 실행 | 서비스   |
| 2. 이벤트 발행   | `OrderPlacedEvent` 발행          | 서비스   |
| 3. 후속 로직 실행 | 재고 차감, 알림 발송, 통계 적재            | 각 리스너 |

---

## **5. 왜 이렇게 나누는가?**

| 장점         | 설명                                              |
| ---------- | ----------------------------------------------- |
| **관심사 분리** | 주문 서비스는 “주문 저장”만 담당하고, 부가 로직은 각 리스너가 담당         |
| **장애 격리**  | 알림톡 서버가 장애여도 주문 저장이나 재고 차감은 정상 처리               |
| **확장성**    | “쿠폰 발급” 같은 새 기능을 추가할 때도 기존 코드 수정 없이 새로운 리스너만 추가 |

---

### **쉽게 비유하자면**

* `OrderPlacedEvent`는 “**확성기**” 같은 역할
* 각 리스너는 “**다른 부서**”

    * 재고팀: 재고 차감
    * 알림팀: 알림톡 발송
    * 데이터팀: 통계 적재

주문이 들어오면 확성기로 알리고, 각 부서가 자기 할 일만 하는 구조라고 보면 이해가 쉽습니다.
