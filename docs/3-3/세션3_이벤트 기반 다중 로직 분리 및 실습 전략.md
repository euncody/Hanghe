이 세션은 **이벤트 기반 아키텍처에서 하나의 이벤트를 여러 개의 독립적인 로직으로 나누어 처리하는 전략**을 다룹니다.
핵심은 **확장성**, **유지보수성**, 그리고 **장애 허용성**이에요.

---

## **1. 하나의 이벤트로 여러 로직을 분리**

### **기존 방식**

주문이 발생했을 때:

* 주문 저장
* 재고 차감
* 알림 발송
* 통계 적재
* 로깅

이 모든 로직을 서비스 메서드 한 곳에서 처리하면 **코드가 복잡**해지고, **한 로직의 실패가 전체 프로세스를 망칠 수 있습니다.**

---

### **이벤트 기반 방식**

하나의 이벤트(`OrderPlacedEvent`)를 발행하고,
여러 리스너가 **각자의 관심사만** 담당하도록 나눕니다.

**예시 구조**

```
[OrderService]
   └─ OrderPlacedEvent 발행
        ├─ InventoryListener: 재고 차감
        ├─ NotificationListener: 알림톡 발송
        ├─ AnalyticsListener: 통계 적재
        └─ LoggingListener: 이벤트 기록
```

이렇게 하면:

* 코드가 모듈화되어 **유지보수 용이**
* 새로운 기능을 추가할 때 **핵심 로직 수정 없이 확장 가능**

---

## **2. 리스너 간 독립성과 장애 허용 설계**

각 리스너는 서로 **완전히 독립적**이어야 합니다.
예를 들어:

* **알림톡 발송 실패**가 발생해도,
  재고 차감이나 주문 데이터 저장은 영향을 받지 않아야 함.
* **통계 적재 서버 장애**가 발생해도,
  메인 주문 프로세스는 정상 처리되어야 함.

이 구조를 통해 **“부가 로직의 장애가 메인 로직에 전파되지 않도록”** 설계할 수 있습니다.

---

## **3. 후속 실패 처리 전략**

부가 로직이 실패했을 때는 **즉시 장애 전파 대신, 후속 처리**를 설계해야 합니다. 대표적인 전략은 아래와 같습니다.

| 전략            | 설명             | 예시                                   |
| ------------- | -------------- | ------------------------------------ |
| **로깅**        | 실패 원인과 데이터를 기록 | `error.log` 또는 ELK로 추적 가능하게 남김       |
| **리트라이(재시도)** | 일정 횟수/시간 후 재시도 | Spring Retry, Redis Queue, Kafka DLQ |
| **알림**        | 운영자에게 즉시 알림 발송 | Slack, 문자, 이메일로 장애 통보                |

---

## **4. 간단한 Kotlin 예시**

### **이벤트 발행**

```kotlin
data class OrderPlacedEvent(
    val orderId: Long,
    val userId: Long
)

@Service
class OrderService(
    private val eventPublisher: ApplicationEventPublisher
) {
    fun placeOrder(orderId: Long, userId: Long) {
        // 1. 핵심 로직: 주문 저장
        eventPublisher.publishEvent(OrderPlacedEvent(orderId, userId))
    }
}
```

---

### **다중 리스너**

```kotlin
@Component
class InventoryListener {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    fun handle(event: OrderPlacedEvent) {
        println("재고 차감 처리: ${event.orderId}")
    }
}

@Component
class NotificationListener {
    @Async
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    fun handle(event: OrderPlacedEvent) {
        println("알림톡 발송: ${event.userId}")
    }
}

@Component
class AnalyticsListener {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    fun handle(event: OrderPlacedEvent) {
        println("주문 통계 적재: ${event.orderId}")
    }
}
```

---

## **5. 이 접근법의 장점**

| 항목        | 효과                        |
| --------- | ------------------------- |
| **확장성**   | 새로운 리스너를 추가해도 기존 코드 변경 없음 |
| **유지보수성** | 로직이 관심사별로 나뉘어 가독성과 테스트 용이 |
| **안정성**   | 부가 로직의 실패가 메인 로직에 영향 없음   |
| **장애 대응** | 로깅, 리트라이, 알림으로 실패 관리 가능   |

---

## **정리**

이 세션의 핵심 메시지는:

* **하나의 이벤트에서 여러 관심사를 독립적으로 처리**하자.
* **부가 로직 실패가 메인 로직에 영향을 주지 않도록 설계**하자.

이렇게 하면 시스템은 **더 안전하고 유연하게 확장**될 수 있습니다.
